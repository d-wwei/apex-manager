# 4 层分工，手搓 Agent 蜂群，真正开启团队作战

别再让 AI 扮演 PM、架构师、程序员、测试，排着队做办公室过家家了。真正能打的 Agent 团队，不是“角色越多越专业”，而是一个 Plan Agent 抓全局，一群全链路 Worker 并行推进，再用独立评审工作模式和状态层把质量与秩序兜住。

## 多 Agent 最大的坑，不是模型不够强，而是分工分错了

很多人第一次做多 Agent，直觉都一样：

- 一个 Agent 写需求
- 一个 Agent 出设计
- 一个 Agent 写代码
- 一个 Agent 做测试

画成架构图，特别像一家小公司。问题也恰好出在这里。

人类团队需要岗位分工，是因为每个人的注意力、技能、时间都有限。LLM 不是。你让同一个模型上一秒写方案，下一秒补测试，第三秒做 code review，它并不会因为“跨岗”而元气大伤。真正让它变笨的，反而是一次次交接。

需求 Agent 交一份摘要给设计 Agent，设计 Agent 再交一份文档给开发 Agent。每一次传递，看起来都很正式，实际上都在压缩上下文。为什么这个方案成立，为什么那个方案被排除，哪里最脆弱，哪里只是临时妥协，最关键的判断往往都不会完整写进交接文档里。

结果就是：每个 Agent 看起来都在认真工作，整条流水线却越来越偏。

多 Agent 真正该解决的问题，从来不是“怎么把 AI 伪装成公司组织架构”，而是两件事：

1. 怎么让全局意图不丢。
2. 怎么让多个 Agent 在不互相踩踏的前提下并行推进。

这就是“手搓 Agent 蜂群”和“角色扮演流水线”的本质区别。

## 蜂群作战，不靠角色扮演，靠共享目标和局部自治

蜂群厉害，不是因为每只蜂都拿着一张工牌，上面写着“产品经理蜂”“测试蜂”。蜂群厉害，是因为它们围绕同一个信号源行动，能并行探索，能快速回传，能持续修正方向。

Agent 团队也一样。

一个能落地的多 Agent 系统，分工应该按信息结构来切，而不是按岗位名称来切。

### 第一层：Plan Agent，负责全局，不负责代做

Plan Agent 只有一个核心职责：持有完整意图。

它要知道：

- 这次到底要做成什么
- 当前任务怎么拆才彼此独立
- 哪些任务有依赖，谁先谁后
- 哪个 Worker 跑偏了，什么时候要纠正
- 哪些结果值得合并，哪些需要打回

它不该替 Worker 设计细节，也不该把自己变成另一个执行工位。Plan Agent 是队长，不是全队唯一写代码的人。

说直白点，Plan Agent 管调度，管优先级，管方向；不管“这一行代码到底该怎么写”。

### 第二层：Worker Agent，必须是完整工程师，不是角色碎片

真正出去干活的 Worker，最忌讳被阉割成“只负责某一小段”的角色碎片。

一个靠谱的 Worker，应该能自己走完完整闭环：

- 理解任务
- 阅读上下文
- 制定方案
- 改代码或写文档
- 跑验证
- 自查风险
- 产出结果

为什么这点这么重要？

因为只有完整闭环，推理链才不会断。它知道自己为什么选这个方案，知道刚刚为了通过测试做了什么让步，也知道哪里还有技术债。出了问题，它能顺着自己的链路回溯；如果只是流水线上的一个“开发 Agent”，它只能把问题甩给上游或者下游。

所以，正确的做法不是把 Agent 分成“产品、研发、测试”三种岗位，而是把任务拆成多个可以并行推进的工作包，然后让每个 Worker 在自己的任务包里独立走完全链路。

### 第三层：验证层，职责是否定，不是接棒

很多人问：如果 Worker 已经自己写、自己测、自己检查了，那验证谁来做？

答案是，要有验证层，但它不是来“接着干”的，而是来“专门挑错”的。

这里我故意不用“Verification Agent 已经是内建一等角色”这种说法。更准确地说，验证应该是一种**独立评审工作模式**：你可以派一个或多个 Worker 去做专门的 review / audit / adversarial check，但它不是今天这版系统里被硬编码成官方角色名的东西。

这个模式最有价值的姿势只有一个：站在对抗面。

它不应该接过上一棒继续生产，而应该拿着同样的目标和结果，专门去问：

- 这个实现有没有漏边界条件？
- 测试是不是只证明了 happy path？
- 这个改动会不会把别的模块悄悄打穿？
- 这份结论是证据充分，还是只写得像真的？

更进一步，验证最好跨模型做。Claude、Codex、Gemini 不需要串成流水线，它们更适合并行独立审查，然后把发现汇总。这不是“角色传递”，这是“并行对抗”。

### 第四层：Daemon / Ledger，负责把状态留在系统里

再强的 Agent 团队，只要状态全靠聊天窗口记忆，迟早失忆。

所以还需要最后一层：把状态外化。

这层不负责思考，负责秩序：

- 谁在运行，谁卡住了
- 哪条消息发出去了，谁确认了
- 哪个任务 claim 了，哪个完成了
- 结果文件在哪
- 哪些 artifact 可合并，哪些还需要复核

没有这层，多 Agent 只是一堆同时打开的终端。看起来热闹，实际不可管理。

## 真正该怎么拆任务？不是按岗位拆，是按依赖拆

如果你也想自己拉一支 Agent 队，最实用的判断标准只有一个：

**这件事的上下文，是必须连续推理，还是可以并行展开？**

可以直接按下面这套判断来拆：

### 适合单个全链路 Worker 的任务

- 需要持续思考才能做对的功能实现
- 中间设计会频繁变化的复杂重构
- 高度耦合、一步错后面全错的改动

这类任务不要硬拆岗位。一个 Worker 从理解到实现到自检跑完整链路，通常比四个角色接力更稳。

### 适合并行多个 Worker 的任务

- 多个子模块边界清晰
- 多条调研线可以同时展开
- 同一个目标下可以做多方案探索
- 不同文件或 worktree 可以天然隔离

比如一个版本上线前，你完全可以同时拉三类 Worker：

- Worker A：实现核心功能和测试
- Worker B：做兼容层、迁移脚本、边界收口
- Worker C：只做对抗审查和风险清单

注意，这里的 A、B、C 不是岗位头衔，而是任务包。

### 一定要单独拉验证层的场景

- 涉及安全、计费、权限、数据一致性
- 变更影响范围大，出事代价高
- 已经出现“自己看自己总觉得没问题”的盲区

这时不要把验证 Agent 变成流水线最后一棒，要让它站到对立面，专门拆台。

## 这正是我们做 Apex Manager 的原因

我们想做的，从来不是另一个“替代 Claude/Codex/Gemini 的超级 AI”。`apex-manager` 的定位更克制，也更实用：它是一个本地、终端优先的多 Agent 编排层，帮你把现有 CLI 真正组织成团队。

它现在已经具备几件非常关键的事：

- Plan Agent 视角的任务创建、依赖管理和调度
- 每个 Worker 独立终端会话
- git 仓库下的 worktree 隔离，减少并行改动冲突
- manager 到 worker 的结构化消息
- daemon 监控、事件账本和状态快照
- `--cross-model` 路径，把多个模型拉进同一任务做并行执行或交叉验证

这套设计的关键，不是“多开几个窗口”。

关键在于它把多 Agent 真正拆成了四层：

- **Plan Agent** 负责拆任务、排依赖、盯方向
- **Worker** 在各自 worktree 里独立干完整任务
- **Independent Review** 可以作为专门的验证工作模式接进来
- **Daemon / State** 负责监控、消息、事件、artifact、可追溯性

这才是团队，不是 cosplay。

## 我们和市面上多 Agent 工具，到底有什么不一样

这块如果不讲清楚，`apex-manager` 很容易被误解成“又一个 agent 编排器”。但它的取舍其实很明确，而且和很多现成方案不在同一个重心上。

### 1. 模型厂原生 team 功能，通常只能在自己的生态里玩

这不是说它们没价值，恰恰相反，模型厂自己做出来的 team/subagent 体验通常非常顺。

但它们天然有一个边界：**默认都是围绕自家 runtime、自家 CLI、自家会话模型来设计的。**

比如：

- Claude Code 的 Agent Teams，是“多个 Claude Code session 组成一个 team”
- Codex 的 subagents，是“Codex 在自己的 app/CLI 里生成、调度、管理子 agent”

它们当然能把并行协作做得很好，但如果你的真实工作流是：

- 这个任务让 Claude 跑
- 那个任务让 Codex 跑
- 另一个任务想接 Gemini 或自定义 CLI
- 还想用统一的任务、消息、artifact、状态账本把它们拉到一起

这时候，原生 team 功能通常就不够了。你需要的是**跨 CLI、跨模型、跨协议的外层编排层**，而不是继续深挖某一家产品内部的 team 能力。

这也是为什么 `apex-manager` 从一开始就不是要做“某个模型厂 team 功能的复刻版”，而是做一个更外层的 Team Kernel：让 Claude、Codex、Gemini、OpenCode 这些异构 agent CLI，能在同一个项目里被统一调度。

### 2. 像 Paperclip 这类工具，产品中心更偏 dashboard / control plane；我们更偏终端原生、本地优先

Paperclip 很有代表性。它的重心不是“让你在终端里带几个 coding worker 把活干完”，而是做一个更完整的 agent 公司控制面：

- dashboard
- agents page
- org chart
- budget / governance
- approval queue
- 实时监控与活动流

这条路线没问题，甚至很强。但它的产品重心明显更靠近“图形化控制台 + 公司运营面板 + 持续运行 control plane”。

而 `apex-manager` 走的是另一条路：

- **纯终端、本地优先**
- **先把当前仓库里的协作跑通**
- **先把 worker worktree、消息、状态、daemon 收紧**
- **先让你今天就能在自己的 CLI 环境里多 agent 开工**

我们不要求你先接受一整套新的前端控制台工作流，再去接现有 agent。我们默认你本来就活在终端里，本来就在用 Claude/Codex/Gemini CLI，所以我们做的是它们上面那层最薄、最贴近工程现场的协作层。

### 3. 我们不是把“终端”做成终点，而是把它当成第一层 transport

这点很关键。

如果一个系统把 `tmux`/`cmux` 直接写死成最终形态，那它就很难继续长大。但 `apex-manager` 的路线不是这样。

我们的思路是：

- 今天先 **terminal-first**
- 先把 Team Kernel 的语义做稳
- 让 task、message、artifact、event 这些核心对象先独立出来
- 再在这个内核外面接别的 transport

所以它现在虽然是本地终端优先，但不是“只会终端”。相反，roadmap 已经明确保留了后续往 **MCP、A2A、ACP** 扩展的路径。

也就是说，今天你可以把它理解成：

- **当前交付形态**：本地、终端原生、跨 CLI、多 worker 协作
- **未来扩展形态**：在不推翻内核的前提下，往跨机器、跨进程、标准协议互通演进

这和“先做一个很重的 web control plane，再反过来兼容终端”是两条完全不同的工程路线。

### 4. 我们的特殊点，不是功能更多，而是边界更克制

很多编排工具喜欢一上来就把“组织架构”“审批流”“业务目标”“控制台”“远程服务”“多租户”全塞进来。看上去很完整，代价是系统会越来越重，也越来越远离真实开发现场。

`apex-manager` 反过来是把边界收紧：

- core 只理解通用 team primitives
- domain workflow 交给 protocol / skill
- transport 可以先用终端，后面再接标准协议
- 本地先跑通，再决定哪些东西值得抽成远程层

这种克制，带来的直接好处就是：它更容易先成为一个**真的能用的工程协作层**，而不是一个概念很满、但离日常开发太远的“AI 公司操作系统”。

## 一个最小可跑的团队作战长什么样

如果你今天就想把“手搓 Agent 蜂群”跑起来，一个最小闭环其实很简单：

```bash
apex-manager init
apex-manager task create "Build API" "Implement the endpoint and focused tests"
apex-manager task create "Audit API" "Adversarial review for edge cases" --depends T1 --agent codex
apex-manager worker spawn T1 --agent claude
apex-manager worker spawn T2 --agent codex
apex-manager orch start
```

这背后真正发生的事是：

- Plan Agent 定义任务和依赖
- Worker T1 在自己的上下文里完成实现闭环
- Worker T2 不接棒写功能，只作为独立评审任务包去挑问题
- daemon 持续记录状态、消息和事件，避免团队失联

如果项目是 git 仓库，每个 Worker 还能拿到独立 worktree。这样并行不是“大家一起改同一份目录赌运气”，而是有文件系统级隔离的。

## 为什么我们更看好“终端优先”的 Agent 团队

很多多 Agent 方案喜欢先做一个漂亮控制台，再想办法把 Agent 塞进去。我们反过来。

先让团队真的跑起来，再谈更大的平台化。

终端优先的价值很朴素：

- 你看得见每个 Worker 在干什么
- 出问题时能直接接管
- 现有 Claude、Codex、Gemini CLI 都能接进来
- 不用等一个全新的封闭平台成熟，今天就能在自己的仓库里开工

这也是为什么 `apex-manager` 不试图替代现有 agent CLI，而是做它们上面的那层编排。好用的 agent 已经有了，缺的是把它们拉成一支队伍的方法。

## 最后一句

“手搓 Agent 蜂群”真正难的，从来不是把多少模型塞进同一个界面，而是想明白一件事：**Agent 应该按什么分工，才能既不丢上下文，又能放大并行效率。**

我们的答案是：

- 不按岗位名分工
- 按任务依赖分工
- 让 Worker 保持完整闭环
- 让独立评审保持对抗性
- 让状态留在系统里，不留在记忆里
